# Itinerary sheet clearance from the mobile composer

The frontend change adds bottom padding to the itinerary timeline so its last content should remain scrollable above the fixed chat composer. The approach combines a fixed `12rem` content inset with the device bottom safe-area inset, while the composer remains an absolutely positioned dock whose contents change between idle and running states. The sheet itself also consumes the safe-area inset. **Watch for:** **confirmed**, the inset is not derived from the composer’s actual height, so the idle suggestions row and an expanded multiline composer can cover the final itinerary content. **Verdict**: NEEDS_CHANGES

## High-level view

The sheet and composer share the same viewport but do not share a measured occlusion boundary. The timeline uses a constant `12rem` plus safe-area padding, whereas the composer’s idle state adds suggestions and its input can grow vertically; this makes the clearance dependent on content state rather than reliably guaranteed (**confirmed**).

Safe-area handling is present in both the sheet shell and the timeline inset, which avoids clipping on gesture-area devices but can add extra clearance because the scroll container already ends above the sheet’s bottom padding (**confirmed**). There are no focused tests for the overlap contract or responsive composer states, so this spacing change is currently validated only by static class values (**confirmed**).

<summary>Details</summary>

### Fixed timeline padding versus variable composer height

`ChatScreen.tsx` gives the itinerary scroll container `pb-[calc(12rem+env(safe-area-inset-bottom,0px))]`. The composer dock is independently positioned at the viewport bottom with `pt-16`, a scroll-to-bottom control, an idle-only suggestions row, the composer controls, and bottom safe-area padding. In the idle state, the suggestions row is present; while a response is running it disappears. The input is also allowed to grow from one row up to `max-h-24`.

That means the sheet’s occluding boundary is not constant. The reserved `12rem` is close to the compact dock’s base footprint, but it does not account for the idle suggestions row and leaves no explicit allowance for a multiline input. A long final stop or action row can therefore scroll into the dock/fade region instead of stopping above the composer. This is **confirmed** from the independent fixed padding and state-dependent composer children; the exact visual overlap depends on rendered font metrics and viewport size.

The fade is not a substitute for layout clearance: it visually masks content behind the composer but does not make that content reachable or readable. The clearance should be owned by one shared measurement/constant, or the sheet should reserve the maximum composer footprint if the design intentionally avoids runtime measurement.

### Safe-area behavior and missing coverage

The dock includes `pb-[max(1rem,env(safe-area-inset-bottom))]`, while `.bottom-sheet` itself has `padding-bottom: env(safe-area-inset-bottom, 0px)` and the timeline adds the same inset again. This is conservative against gesture-area clipping, but it means the child scroll viewport already ends above the sheet bottom while its scroll padding also includes the safe area. The resulting extra gap is **confirmed** from the nested padding declarations; whether it is visually excessive depends on the device inset and sheet height.

No frontend test found in the current tree exercises this relationship (**confirmed**). At minimum, the spacing behavior needs coverage for idle suggestions, running response, expanded input, and a nonzero safe-area inset; otherwise a future composer control can silently invalidate the fixed `12rem` assumption.
